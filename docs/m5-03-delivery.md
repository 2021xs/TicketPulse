# TicketPulse M5-03：ClickHouse 运营统计高并发性能专项

固定 4 GiB ClickHouse 资源下，10 万工单、97.5 万历史的完整运营看板已稳定验证到 **20 并发**。最终源码的 120 秒大组织完整窗口测试全部成功，完成吞吐 24.37 QPS，p95 942.65 ms、p99 1025.969 ms；混合组织／团队／窗口看板约 30–32 QPS。50 并发短测有时成功，较长测试出现内存失败与超时，不能承诺稳定支持。

本轮基于 live repository、M3 冻结口径及 M5-01 原数据规则，完成两项局部优化：每张表只扫描一次、按工单选择首次／最新版本；利用既有物理排序限制聚合与读取块的内存。没有增加 CK 内存、改变表模型、同步协议或 M4 恢复协议，没有引入物化视图或跨请求缓存。源码未暂存、提交或推送。

## 真实统计链路与 M3 口径

主管请求先完成当前身份与权限核验，再读取 Kafka 分区进度和 CK 指标，最后由 Go 组装完整概览、每日趋势、团队指标和平均时长。一次 HTTP 请求计算全部统计项目，没有单指标产品接口。普通用户无法通过客户端角色或组织字段取得权限。

~~~text
GET /api/v1/analytics
  → 当前用户 / 主管权限 / 日期与团队参数
  → Analytics Service / AnalyticsAccess / AnalyticsStatus
  → ClickHouse.Metrics / 参数化 SQL
  → ticket_events + ticket_states
  → 按日和团队汇总 / 平均首次解决时长 / 当前积压
  → 完整 HTTP JSON
~~~

事件来自已提交 MySQL 工单与同版本不可变历史，经过原 Binlog → Kafka → 独立 CK 消费组。两张普通 MergeTree 表追加写入，排序键均为 `(organization_id,ticket_id,version)`，没有日期分区、投影、持久预聚合或物化视图。Kafka 重放和 M4 回填可能写入相同业务版本，物理行数不能直接作为业务计数。

| 统计 | 冻结含义 |
| --- | --- |
| 新增 | 创建动作的最小业务版本；初始团队；北京时间日期，左闭右开 |
| 首次解决 | `resolved` 且到待确认的最小业务版本；事件当时团队；再次解决不增加首次计数 |
| 平均时长 | 首次解决时间减创建时间；先累计整数微秒，再换算秒并除首次解决数 |
| 当前积压 | 每工单最大 `(version,complete)` 的状态，待处理／处理中；当前团队；与日期窗口无关 |
| 数据状态 | 当前工单观察数与原分区同步状态；空空间保留 observed=0 |

原 SQL 先按组织／工单／版本归并事件，再分开取创建与首次解决；首次解决连接创建以计算时长。新增分支、解决分支和连接右侧重复展开事件 CTE，积压与 observed 分支重复展开最新状态。最终执行计划有三次事件表读取、两次状态表读取。组织主键裁剪已生效，普通日期／团队过滤主要在首次或最新选择后发生。

不能把时间窗口或团队过滤直接推到原始行：窗口内的再次解决可能替代窗口外首次解决；仅保留当前团队行会丢失后续转派版本；仅保留待处理状态会漏掉后续解决或关闭。最终查询仍在版本选择之后筛选。相关源入口见文末代码索引，原 SQL 与计划保存在 [original](../artifacts/m5-03/sql/original/) 和 [原计划](../artifacts/m5-03/sql/final-plans/original/)。

## 独立数据、预算和测量方法

数据来自原 `ticketpulse-benchseed/v1`、seed 20261109。1 万／10 万分别有 97,500／975,000 历史，首次解决 4,000／40,000、重开 3,000／30,000、当前积压 7,000／70,000。Bundle SHA256 与 M5-01 冻结 manifest 完全一致；没有以正式 SQL 生成预期。另复制前 10% 工单形成非空组织 2，团队 10／20／90 映射到 200／210／290，用于验证组织裁剪。主组织 MySQL 源保持原完整数据。

10 万主组织 CK 实际有 975,475 物理事件、1,075,525 物理状态；规范历史仍为 975,000，最新状态仍为 100,000。状态表包含每个历史版本、权威当前快照和重复写入，没有事先清洗成仅十万当前行。输入与哈希见 [数据 manifest](../artifacts/m5-03/datasets/)、[冻结验证](../artifacts/m5-03/datasets/100000/attempt-v2/verification.json)。

测试使用单独 CK 18125／19003、MySQL 33308、HTTP 18086，数据与原演示隔离。CK 资源保持原 M5 4 GiB、单查询 512 MiB、64 个服务并发名额和相同 query_log／query_thread_log 设置；最终 SQL 的线程与块设置属于查询优化。没有通过请求拒绝、指标减少、窗口缩小或增加内存取得吞吐。

冻结夹具直接投影数据，没有创建百万条消费进度记录；测试 HTTP 仍执行真实当前权限与状态入口，但该空间显示未获得实时同步证明，消费记录表较小。组织 1／2 的 Topic 与分区状态查询实际存在。这建立 CK 统计查询容量，不代表生产状态查询、持续 CDC 与业务写入的整体吞吐；真实 CDC、分区 ACK 和追赶正确性另由 M3/M4 回归验证。

闭环请求分布循环覆盖组织 1／2、全部／单团队／双团队、1／3／8／30 天窗口。短测入场 10 秒、预热 2 秒；稳态入场 120 秒、预热 3 秒。每个目录保存 input、预热与正式逐请求、HTTP/CK 错误、结果哈希、0.5 秒资源采样、Part 前后、完整 query_log；query_log 的内存为查询峰值，ps 的 RSS 和 CPU 是独立进程观测。CPU 100% 表示占用一个核。

预算为 CK 受跟踪内存 4 GiB、RSS 6 GiB、单轮新增磁盘 20 GiB。后期压测器在任意 CK code 241 或 HTTP 不可用时停止新请求；早期 0.5 秒探针会漏瞬时超限，HTTP 的统一不可用映射也未及时触发停止，所以两个较长 50 并发失败实验运行到了固定时长。该偏差保留在 [失败实验](../artifacts/m5-03/failures.json)，只作为失败边界，不作为成功容量；最终 50 并发在预热第一次不可用后立即停止。所有实验新增磁盘低于 20 GiB，没有清理原演示或旧证据。

两轮 A/B 顺序分别为原版→优化、优化→原版。主数据 Merge 在测量中暂停，第一轮早期 CK 原版的 7 个事件 Part 在重启后合并成 5 个；后续所有 HTTP 对照和第二轮都使用相同的 5 个事件／3 个状态 Part，各轮内部不变。早期 CK 对照不能声称 Part 完全相同，见 [Part 审计](../artifacts/m5-03/environment/ab-parts-count-audit.json)。最终又在同一实例、无重启、相同 Part 下完成 [补充 A/B](../artifacts/m5-03/final-ab/)。

## 原查询瓶颈与方案选择

主要瓶颈是多次高基数版本聚合与读取缓冲的内存叠加。原 10 万完整窗口读取约 509 万行、202 MiB，查询峰值约 334 MiB；10 个同时运行就可能加上 CK 本体、日志与后台 Merge 后触及 4 GiB。实际 code 241 明确记录 `(total) memory limit exceeded`、OvercommitTracker 以及 `AggregatingTransform`，也有读取阶段失败。它不是单纯 HTTP 连接不足或磁盘不足。

单指标顺序诊断把成本拆开：积压读取约 108 万状态行、峰值约 66 MiB；新增与首次解决各读约 97.5 万事件行、峰值约 122–123 MiB；平均时长连接两侧事件，各合计约 195 万行、峰值约 136 MiB。单指标在 10／20／50 的并发原始结果见 [分解压测](../artifacts/m5-03/diagnostic-metrics/)，多数事件类档位触及预算，不能作为持续 QPS。顺序计划、各组织／团队成本、CPU 和完整 query_log 见 [final-plans](../artifacts/m5-03/sql/final-plans/)。

候选比较先保留证据，再决定落地；下表的数据是顺序单请求或候选短测，不替代稳态容量。

| 方向 | 实际发现 | 取舍 |
| --- | --- | --- |
| A：原 SQL＋计划与裁剪 | 仅开启有序聚合的默认 50 MB 聚合块仍会占较多内存；限制块后峰值约 138 MiB，但仍五次读取，50 并发失败 | 保留有序与小块机制，单独方案不足 |
| B：复用规范事实 | 查询内物化 CTE 将物理读取降到两次，但保留约 189 MiB 中间结果，20／50 并发仍失败；直接按工单取最小／最大版本可减少重复聚合和连接 | 采用每工单一次计算，未采用物化 CTE |
| C：持久预聚合／物化视图 | 原表、已有最小／最大版本事实足以支持局部查询优化；每批原始 count/sum 会被 Kafka/M4 重放增加计数 | 本轮不引入；未改数据模型或同步协议 |
| D：有限并发／背压 | 可保护 4 GiB，但排队／拒绝不降低实际查询成本，且必须另报排队与尾延迟 | 本轮未加；20 并发是实测边界，不是代码限流 |

最终保留两项局部优化。第一项把创建、首次解决与时长放在同一工单聚合中，状态也只算一次，然后展开成各指标；相同版本的完全相同重复行不会改变 min/max 选择。第二项在该 SQL 内设置有序聚合、128 KiB 聚合块、1,024 行读取块、关闭有序读取缓冲和单查询／最终聚合线程各 1。表、写入、Kafka ACK、M4 分批与接续均未改变。

最终还执行精确冲突检查：同一工单的“完整业务版本内容去重数”必须等于“版本键去重数”。事件比较包含业务事件 ID、动作、时间、历史团队、初始／前团队、前后状态、负责人、创建与首次解决时间；状态比较包含 `(version,complete)` 和全部业务状态字段。NULL 保留在 tuple 内，运输事件 ID 和写入时间不参与业务相等。冲突即使在旧版本或筛选范围之外也使整条查询失败，不能静默选任意行。

新增冲突拒绝曾使已确认差异的原 M4 对账变成 uncheckable。本轮做最小兼容修正：全量比较已经证实 CK 同键冲突时，省去不可信的指标查询，保留差异并继续原源后摘要／水位判定；正常数据仍计算全部指标。M4 的源变化优先级、失败状态与恢复协议未变，原回归已验证。

未带请求内冲突检查的候选曾达到约 94–107 QPS，但它没有进入正式实现。不能把这个数作为交付容量。最终查询的顺序 CPU 成本约 0.37 核秒，查询峰值约 58 MiB，读取约 206 万行／169 MiB；单线程单请求墙钟约 394 ms，未必比原双线程 332 ms 更短，收益主要来自高并发内存、总 CPU 工作量和成功率。

## 正确性、失败恢复与回归

M3 原十工单 Gold 保持人工预期：新增 10、首次解决 6、平均 60,600 秒、当前积压 5；每天与历史团队均按原 JSON 逐项核对。原版与优化后真实 MySQL/Binlog/Kafka/CK Gold 回归通过。新增实验实际发送重复首次／再次解决、迟到创建／转派／重开 Kafka 消息；真实 HTTP 第三次解决、重开、跨团队转派、再次解决和重开后，历史每日指标与首次团队不变，当前积压从 5→4→5，转派后团队积压正确变为 2／3，后续时间窗口首次解决数为 0。

同键冲突实际注入历史团队、动作、NULL 负责人、首次时间以及旧状态字段，全部使 HTTP 返回 503，且旧版本、无关日期与团队不能隐藏冲突；恢复正确物理行后 Gold 再通过。真实 CK 写入成功后 MySQL 消费进度失败造成未提交 Offset，重启后物理重放，正式结果不增加；M4 的回填重放、进度失败续跑、SIGKILL、丢失接续区间、目标损坏和源变化判定都通过。

## 容量边界与预聚合判断

20 是已验证的并发点，不是数学上的最大值；21–49 未逐档测量。最长稳态为 120 秒，尚未验证多小时负载、冷缓存、固定 CPU 配额、多实例、更多组织、100 万工单、366 天真实历史或远超每工单 40 个版本的链路。生产峰值 CDC＋M4 重建＋看板同时运行也未建立容量，详细 query_log 的 Merge 对内存有影响。完整边界在 [remaining-risks](../artifacts/m5-03/remaining-risks.json)。

当前不建议引入持久预聚合／物化视图。查询局部改写已经把内存显著降低，并在保留每请求冲突检查的条件下恢复 20 并发；直接对每批原消息 count/sum 无法满足重放、首次解决、重开和团队归属。若未来必须支持持续 50 并发以上，应另行设计业务键＋版本的规范状态、撤销／修正与冲突拒绝机制，证明重复写入、旧版本迟到、首次解决只一次、最新状态与历史团队的等价性，再经用户确认改变数据模型或同步协议。

未加限流或排队，因此本轮拒绝数为 0（已有 CK 内存失败不是新增 admission 拒绝），没有隐藏排队换取 QPS；客户端并发等待、CK Overcommit 等待和尾延迟都包含在 HTTP 结果。未来背压可以保护服务，但需要单独报告完成吞吐、排队时间、拒绝与尾延迟，不能混入本轮代码优化收益。
