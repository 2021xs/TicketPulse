# TicketPulse M5-01 性能基准与恢复规模调查

本轮回答本机真实跑到的规模、并发和恢复边界，并交付两项有实测依据的有限优化。**最大实际数据规模为 10 万张工单；百万级未执行。1 万张档位的核心读在 200 并发下完成两次无错误短测，约 3,357～3,413 成功 QPS。10 万张档位恢复后的数据内容通过独立全量核对，但正式 M4 对账因 MySQL 查询读超时失败，不能称为完整恢复验收成功。**

结论标签：CODE 表示当前源码可确认；RUNTIME 表示真实组件观测；INFER 表示基于证据的推断；UNKNOWN 表示本轮没有充分验证。本文的 QPS 均来自请求数除以实际完成窗口，没有从并发数换算吞吐。没有找到可独立复核的 PRD 性能阈值，因此不宣布达到业务性能目标。

## 瓶颈证据和两项优化

### 搜索连接池等待链

CODE/RUNTIME：搜索先开启请求授权的RR只读事务，占用一条池连接，再调用同步状态读取，后者向同一个DB池申请连接。50路并发时池20条全部InUse、Idle0，堆栈显示多个SearchFreshness阻塞于DB.conn。连接必须等请求超时释放，形成连接资源等待循环。该现象在三次相同50路负载中复现，成功吞吐17.2～23.4 QPS，p95约5秒。

修复只把同步状态查询放到开启授权事务之前。当前身份、团队、授权和业务版本复核仍在原RR事务，游标与返回内容合同保留。同种子、同数据、同池20、同核心读负载下，修复后三次50路均无错误/超时，p95 23.5～27.3 ms。新增单连接池并发测试直接验证此等待链，不依赖扩大连接池。全仓单元与race、真实M1/M2/M3回归通过。证据见 [连接池调查](../artifacts/m5-01/search-pool-investigation/summary.json)。

### M4快照批量写入

CODE：原批次仅限制源扫描，仍逐事件分别请求ES及CK。现在每个下游请求最多500行、4 MiB；ES每项保留strict external version并校验ID/版本/状态，只有真实版本冲突409可安全无操作；CK显式列、同步JSONEachRow。整批有限重试，ES、CK事实及当前全部成功才更新原持久游标。失败重放可增加CK物理行，规范业务键去重不变。冻结事务、独立Kafka tail、实时消费者、事实模型和源摘要未改。

MySQL tuple分页的等价OR实验保留在keyset-audit，晚页SQL中位数当前16.10→11.20ms、历史79.87→32.21ms，五次同页摘要一致。它没有解决早页重复扫描与排序；最终撤回该正式代码试改，保留本轮两项优化。固定组织/有序扫描方案需要完整跨组织回归及长事务评估，作为下一轮建议。

## 全链路观测与限制

RUNTIME：MySQL配置64 MiB缓存远小于10万源表2 GiB及冻结表。进程列表可见列表查询和历史分页；10万冻结同时200读时MySQL日志在03:21:17 UTC明确记录“Error in accept: Too many open files”，当时测试出现大量内部错误、EOF和监测连接失败。当前open_files_limit8074、table_open_cache4000，既有测试创建过大量随机表；资源耗尽来源是累积表/文件与并发叠加，本轮没有证明仅业务连接数是原因。只读恢复后演示数据哈希保持原样。

MySQL慢查询日志未启用，performance_schema摘要容量已满且存在digest_lost，目标随机库缺少摘要不能被解释为SQL零延迟。表索引IO、事务、锁等待、History list length、磁盘IO与CPU/RSS有真实采样，但主机与实例级数据不能精确归因到一条业务SQL。Undo字节没有完整可靠序列，保留UNKNOWN。

RUNTIME：Kafka3分区，捕获单进程，ES/CK各一进程；代码中每分区顺序处理，实际测试没有多实例并行扩容。每分区Lag及发布/消费Offset有采样，1万真实HTTP写后两组Lag均0；最终10万两组各分区Lag均0。M4源码水位三分区确认已在日志记录。后台周期性水位消息也增加Offset，不能把所有Offset差当业务CDC速率。没有broker JMX，字节生产/消费峰值、稳定CDC最大吞吐和端到端p99可见延迟UNKNOWN。SQL预装载没有压测实时初始灌入。

RUNTIME：ES授权每批100候选、最多2000；正常搜索页20，经MySQL版本匹配与权限复核，可观察约100候选每次复核。首个调试采样537,600候选均授权，属于正常选择性；它不是授权选择性很低的结果。节点search线程池未见拒绝。200路团队过滤及读写混合出现SEARCH_UNAVAILABLE，尚无足够逐请求原因区分连接/HTTPtransport/候选预算，不将它解释为ES集群极限。

RUNTIME：原1 GiB CK单并发规范统计约72ms，扫描312,725行、12.94MB、峰值约63.4MB；10并发均触发code241总内存拒绝。新4 GiB实例10并发统计一次全部成功，50并发仍有code241，错误明确RSS约4.02GiB超过总内存4GiB。新配置收益与代码优化分开，不能作为代码A/B。单查询规范SQL在10万源最终观测0.472秒、读取3,126,515行/129.36MB、峰值291.7MB，输出52行；这是单次CK SQL探针，未做10万统计HTTP并发矩阵，不证明稳态吞吐。

INFER：10万下单长冻结事务已是明确资源成本，约216.8秒相比1万10～17秒明显增长；控制表和Binlog写放大不可忽略。不过端到端最先阻止验收的是对账历史扫描/排序和连接读超时，不能仅把所有瓶颈归给freeze。提高缓存或放宽超时需要在独立组件配置下重复验证；改变冻结一致性协议需另给方案并由用户决定，本轮未实施。
