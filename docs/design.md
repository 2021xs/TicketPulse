# TicketPulse 数据模型与事务设计

工单、创建历史和创建幂等结果必须同时提交。实现使用单个 MySQL InnoDB 数据库和 Go database/sql 的原生事务，业务写入不依赖 RPC、消息队列或跨库事务。M2 增加独立 Binlog → Kafka → 独立 ES／CK 投影，权威写入仍只依赖 MySQL。本地实例已在 MySQL Community Server 8.4.5 验证；DDL 使用的 CHECK 约束要求 MySQL 8.0.16+，其他版本尚未执行验证。

## 数据模型

M1 完整 DDL 的唯一来源是 `db/schema.sql`。已有库按显式迁移推进，M1-04 的 005 要求 004 已应用。M1 有九张业务/身份表，成员关系、评论、密码账号和会话分别保存；M2 的 006 另建三张同步控制表，其唯一 DDL 来源为该迁移，捕获和授权设计见 [M2-01 交付](m2-01-delivery.md)。

| 表 | 内容 | 主键与核心索引 |
| --- | --- | --- |
| `users` | 姓名、有效状态、组织、角色、预置凭据 hash、时间 | id 主键；auth_token_hash 唯一；(organization_id,id) 唯一供外键使用 |
| `teams` | 支持团队名称、组织、有效状态、时间 | id 主键；(organization_id,id) 唯一 |
| `team_members` | 团队与有效账号关系、成员是否仍有效 | (team_id,user_id) 主键；组织/用户/有效性索引 |
| `tickets` | 当前状态、创建/负责人员、初始/当前团队、版本和生命周期时间 | 创建人、当前团队/状态、负责人及组织/状态索引；按更新时间/主键降序 |
| `ticket_histories` | 操作身份、版本、前后状态 JSON、原因、评论关联、操作时团队与时间 | (ticket_id,version) 唯一；评论关联外键携带组织和工单 |
| `ticket_comments` | 作者、正文、工单版本、创建时间 | (ticket_id,version) 唯一；组织/工单/时间/id 稳定顺序索引 |
| `ticket_create_requests` | 当前提单人和 request_id、内容 SHA-256、最终工单 ID、时间 | 自增 id 主键；(creator_id,request_id) 唯一；ticket_id 唯一 |
| `login_accounts` | 用户账号和 bcrypt 密码 hash | user_id 主键；username 唯一；用户外键 |
| `user_sessions` | 随机会话 hash、创建/到期/撤销时间 | token_hash 主键；用户/到期索引；用户外键 |

Ticket 支持请求中的全部核心字段，并保存 PRD 的 reopen_count。M1-02B 通过显式迁移 003_resolution_note.sql 增加可空 TEXT 字段 resolution_note，保存最近解决说明，历史 JSON 保存每次原文。已有工单、历史和幂等记录不重建或改写。时间是 DATETIME(6)，连接会话和 Go 模型统一使用 UTC；空负责人、首次解决时间和关闭时间为 SQL NULL。状态、类别、优先级、文本长度与正版本由 CHECK 约束防止非法值落库。

跨对象外键携带组织字段，防止把当前组织的工单指向其他组织的账号或团队。没有级联删除规则，用户/团队/历史仍被引用时不能物理删除。账号和团队的失效使用 active 标记。每张工单只保存当前状态；历史 JSON 保存操作时的业务状态，用于审计，不是提前构造的分析宽表。

详情按工单主键读取，授权成员查询使用成员主键，历史使用工单/版本唯一索引。三个基础列表使用当前权限 SQL 过滤；创建人和团队队列索引已由 004 改为更新时间排序，并补负责人及组织/状态索引。

## 创建事务

应用层先校验字段和固定枚举、计算创建内容指纹，再交给数据库仓储执行一个 READ COMMITTED 事务。

1. 用 FOR SHARE 读取有效创建人，取得权威组织；账号失效则拒绝。
2. 插入创建请求预留行，数据库唯一键决定请求是否新建。预留行的自增 ID 同时用作工单 ID。
3. 按类别映射、默认团队顺序读取候选团队。只接受同组织有效团队，FOR SHARE 保持本事务期间有效性判定不被并发修改。
4. 用该 ID 生成唯一工单号，初始化 pending、空负责人、version=1，写入 Ticket。
5. 写入创建历史，before=null，after=初始状态，负责团队与创建结果一致。
6. 在同事务内给请求预留行填入最终 ticket_id，要求只更新一行。
7. Commit 成功后才返回 HTTP 201。前面任一步失败均回滚，不提交没有 ticket_id 的预留行。

数据库自增代替额外的发号服务。工单号为 TP-加至少 12 位十进制 ID，现有全局唯一约束比 PRD 的组织内唯一更严格。事务回滚和唯一键竞争会消耗序号，间隙不表示工单丢失；不提供连续无缺号合同。

## 幂等与并发

request_id 使用 VARBINARY(64)，保证大小写与尾部字节比较不受文本排序规则影响。创建内容 hash 的输入是固定字段顺序的标题、描述、类别、优先级；JSON 排版及属性顺序不改变内容身份，业务字符串中的空白变化视为不同内容。用户与请求唯一键定义作用域，不依赖内存锁或“先查后写”。

并发的相同用户/请求插入会在 MySQL 唯一键处等待。胜方提交后，另一方收到 1062，再在 READ COMMITTED 事务中读取已提交记录。hash 相同则读取原工单并返回 200；不同则返回 409。胜方回滚后，待定的插入可继续创建，最终仍至多一个结果。新的创建意图使用新的 request_id，不同用户互不冲突。

成功重试发生在团队重新校验前，原工单不会因为路由改变或团队后来停用而重新创建。创建结果按原工单 ID 回读权威业务状态。数据库返回 Commit 错误时标记结果待确认，不宣称事务一定失败；原 request_id 可安全重试。

本轮保留窗口为**持续保留**：创建请求记录与历史不自动过期，也不提供清理接口。这样数据库保留期间都能满足原请求重放，代价是每次创建保留一条幂等记录。未来缩短窗口或清理前须冻结 API 保证时长、超过窗口后的新意图规则、历史保留与删除合同，并保留自增发号的高水位；不得通过 TRUNCATE、重建发号表或先删唯一键记录缩短当前合同。

## 详情快照与权限

详情用 REPEATABLE READ 只读事务。有效用户、工单、当前团队、成员关系、负责人、历史和评论都从同一数据库快照读取，因此不会混用一个版本的工单和另一个版本的历史。

提单人凭 creator_id 查看本人工单。非创建人 Agent 必须仍属于当前负责团队，用户、团队和成员都有效。Supervisor/Admin 仅在其组织范围内查看。快照在每次请求开始时重新建立，不使用缓存角色、客户端角色或初始团队授权；已经在处理中读取的请求遵循它开始时的数据库快照，提交后新请求立即读取新的权限。

历史按 (version,id) 升序，版本唯一约束使相同工单不会出现两条同版本的业务历史。认领、开始处理、解决、重开与关闭都把业务状态修改、version 递增与历史插入放在同一事务，并检查期望版本。

## 认领与开始处理事务（M1-02A）

本轮使用已有表结构。新的两个用例进入 Store 后执行 READ COMMITTED 事务，按“有效用户→工单→当前团队/成员”的顺序锁定数据：用户 FOR SHARE，工单 FOR UPDATE，成员与团队的联表查询 FOR SHARE。这使同一工单的两个动作串行化，也使授权依据在动作提交前保持有效。

纯业务规则在 Ticket.Claim 与 Ticket.Start：检查 Agent 角色、组织、期望版本、状态与当前负责人。Store 在这些规则前查询当前有效成员关系。认领设置当前用户为负责人，状态不变；开始处理只允许当前负责人并改为处理中。两个用例均递增版本，Store 设置 UTC 微秒更新时间；若时钟值未超过旧更新时间，则增加一微秒保证该字段向前。

更新 SQL 只写 assignee_id、status、version、updated_at，WHERE 带 organization_id、id、expected_version，要求恰好一行。随后用创建流程共用的 insertHistory 写前后状态、动作、操作者、新版本与操作时团队。更新或历史失败都回滚，Commit 确认成功后返回工单；没有提交后异步历史。

同一个旧版本只执行一次。成功者锁内写入新版本后，等待的请求看到新值并返回 VERSION_CONFLICT，不再插入历史。匹配新版本但负责人已存在返回 ALREADY_CLAIMED；状态不允许返回 INVALID_STATE。提交确认丢失与 HTTP 响应丢失都要求先回读详情，本轮不保存动作重放记录或自动换版本重试。

成员查询和历史插入是从 M1-01 原有 SQL 抽取的帮助函数；详情继续使用非锁定的只读快照，创建继续使用持久请求唯一键。M1-01 的 DDL、路由配置、创建幂等和依赖没有修改；种子数据及显式迁移只补同团队第二位测试工程师。

## 解决、重开与关闭事务（M1-02B）

已有 updateAction 固定要求 Agent 与团队成员，不能直接执行提单人动作。本轮只将此授权分成两个明确分支：认领/开始/解决要求有效 Agent 和当前团队成员；重开/关闭要求当前用户就是创建人。其余事务顺序、FOR UPDATE 工单锁、版本条件、每版唯一历史和 Commit 后返回均沿用原实现，没有通用状态机框架。

Store 为每个动作生成一个 UTC 微秒时间，并传给业务规则和历史。首次解决在 FirstResolvedAt 为 null 时写入该时间；再次解决保留原值。重开增加一次 ReopenCount，保留负责人、首次时间和最近解决说明；关闭写入 ClosedAt，不重置首次时间与次数。最终 UPDATE 同时写入状态、版本、负责人、说明及生命周期字段，随后用原 insertHistory 写对应版本的 before/after。

M1-02B 原来在负责人失效时拒绝重开。M1-03 按用户明确的新合同替换这一分支：先锁定并检查当前团队；团队有效而负责人失效时重新入队，团队失效时使用管理恢复。正常重开保留有效负责人，确认关闭仍不依赖负责人在岗。

重开与关闭竞争同一待确认版本时在同一个工单行锁上串行，只有第一项成功更新，第二项看到已递增版本而返回冲突。任一历史写入失败都会回滚状态、版本、时间、说明和次数。旧版本重试不能重复解决、重开或关闭；动作结果未知仍先回读详情。

## M1-03 转派、恢复与评论事务

新增动作继续调用 updateAction。有效操作者 FOR SHARE、当前工单 FOR UPDATE；目标团队、有效 Agent 账号及成员关系在同一事务内 FOR SHARE 检查。只给同团队转派开放主管/管理员分支，认领/开始/解决仍要求当前有效 Agent。工单状态、当前团队、负责人、版本、时间及生命周期字段用一个版本条件 UPDATE；评论插入、历史及业务更新在同一 sql.Tx 内提交。

同团队转派保持状态，允许有效当前负责人或组织主管/管理员指定当前有效团队的其他 Agent。主管可为无负责人的待处理工单分配人员，或替换已失效的处理人。跨团队转派仅管理角色，清空旧负责人、回到待处理；初始团队不变。历史用一条记录保存完整前后状态及原因，responsible_team_id 为生效后的新团队，旧记录保留原团队。转派出的旧团队成员在提交后的新请求中不再有查看、评论或处理权限。

异常恢复只从待确认执行，所有成功重开递增一次版本和重开次数，保留首次解决时间和各次解决说明。它没有放开已关闭重开或待确认直接转派。

| 操作与条件 | 目标状态/负责人 | 历史与失败行为 |
| --- | --- | --- |
| 提单人重开，团队及负责人有效 | 处理中，保留负责人 | reopened |
| 提单人重开，团队有效、负责人失效或为空 | 待处理，清空负责人 | reopened_requeued，系统原因说明异常重新入队 |
| 提单人重开，当前团队失效 | 保持待确认及旧数据 | TEAM_UNAVAILABLE，指向主管恢复 |
| 主管带原因重开，保留有效当前团队 | 负责人有效则处理中，否则待处理/空负责人 | management_reopened |
| 主管带原因重开到不同有效团队 | 待处理，新团队、空负责人 | management_reopened，before/after 保存两团队 |
| 提单人确认关闭 | 已关闭，设置关闭时间 | closed |
| 主管/管理员带原因关闭 | 已关闭，设置关闭时间 | manually_closed；没有任意时长阈值 |

评论采用独立表。有效创建人、当前有效团队 Agent 和组织管理角色按详情同一授权规则写入；评论正文、作者和时间不会由客户端身份指定。每次评论增加工单版本及更新时间、写一条关联 commented 历史。这样未来 CDC 能根据权威版本和历史识别评论业务变更；M1 未实现任何异步传播。已关闭工单允许授权评论，状态及关闭时间不变。旧版本重试不能再次追加正文。

004 迁移新增评论表，历史增加可空原因与评论关联，旧工单和历史 JSON 不改写。CHECK 要求管理例外、跨团队转派及异常重新入队有原因，commented 必须关联评论；外键防止跨组织或跨工单关联。迁移按一次执行，DDL 每语句提交，部分失败后需按实际信息结构恢复，不以重建表回退。

## M1-03 三个固定列表

列表与详情一样在每个请求重新建立 REPEATABLE READ 只读快照，有效用户、授权 COUNT 和分页数据在同一快照读取。SQL 先限定组织，再限定创建人/负责人/当前团队。成员关系用 EXISTS，兼容多团队，避免重复工单和不受授权的计数；不会先抓取无权结果再在 Go 丢弃。

默认更新时间降序、同时间用工单 ID 降序。每页 1–100 行，page 最大 10000，固定数据集稳定；持续变更时各页不是一个长期快照。Agent 的团队队列是其全部有效成员关系，主管/管理员队列为组织内有效团队，普通提单人无处理队列。分配给我的仍组合当前详情权限，成员失效不能单凭旧负责人字段继续读取。

## M1-04 Web、会话与候选查询

Web 用同源 HTML、CSS 和 ES 模块，资源由 Go embed 随二进制提供。页面调用原列表、详情和动作接口，后端事务及状态规则不重建。页面根据服务端候选能力显示控件，每次动作仍携带读取版本，Service/Store 重查权限。评论、解决说明失败保留草稿；创建意图按用户保留 request_id 和内容，结果未知时原内容锁定供安全重试。

005 新增 login_accounts、user_sessions，不改写原用户/团队/工单。合成密码为 bcrypt cost 12；用户名独立唯一，种子只补缺失账号。密码校验后在事务内锁定有效用户及当前密码记录，再生成创建/到期时间并提交随机凭证的 hash；响应通过 HttpOnly Cookie 提供凭证，数据库不存原文。会话绝对到期 8h，再次登录轮换旧 Cookie，退出设撤销时间。读写实时检查会话和账号，不滑动续期；重启仍从 MySQL 读取会话。

Cookie 写请求要求同源 Origin 及绑定秘密会话的 HMAC CSRF；原 Bearer 保留，不允许无效 Bearer 回退 Cookie。登录也做 Origin 校验。SameSite=Strict、HttpOnly、CSP、无 CORS 放行配合安全文本渲染。localhost HTTP 没有 Secure，HTTPS 或显式参数启用。当前没有会话后台清理、账号管理或登录限流。

当前用户接口从同一只读快照读取账号及有效成员团队，返回静态类别/优先级合同。候选接口先复用详情授权，再按当前团队、有效 Agent 和角色/状态提供候选及动作；原写接口重新核验。详情仅增加本工单及历史引用的参与人/团队显示数据；列表增加当前团队名，原授权和排序保持。

make setup 可对已有 M1-03 库保留数据并应用 005，重复执行保留密码；部分迁移状态显式失败供恢复。浏览器夹具创建随机库、启动独立 18081 服务，用真实 Chrome 完成业务流程，结束只删除该测试库。故障注入及账号/团队失效仅在测试库，现有演示数据保留。

## Kafka 发布与消费边界（M2-02）

架构和迁移合同见 [M2-02 交付](m2-02-delivery.md)。业务事务只写 MySQL，捕获仍是原 Go Binlog 实现，事务内多表聚合到工单／版本消息。每条输出由 Kafka 确认后才保存捕获检查点；部分发布失败时重启从前一个检查点重读，允许重复。检查点与 Kafka 消费 Offset 分别代表“可靠发布到日志”与“投影完成或持久隔离”。

Topic 默认三分区，Key 为十进制工单 ID。每个分区顺序处理，分区间并行；关闭自动提交，持久写入或隔离完成后同步提交下一 Offset。暂时失败留在原 Offset，失败分区暂停退避，其他分区继续。失败记录以 Topic/Partition/Offset 为唯一键，ES 和 CK 分表，重投保存原消息及恢复 Offset。消费批次有时间上限，阻止处理中撤销归属；未完成批次可重读，MySQL 处理记录不替代 Kafka 提交。

008 只新增同步控制表。旧检查点必须显式迁移，旧日志仍覆盖起点才允许切换。保存 Topic ID 防止同名 Topic 重建后沿用旧起点。事件 Topic 禁用自动时间／容量过期；磁盘不足导致发布失败和捕获停留，后续需要明确清理策略。单节点副本 1 仍是原演示默认条件。[M4-02](m4-02-delivery.md) 在独立 Kafka 4.4 三进程集群验证了副本 3、最小 ISR 2、单节点故障与恢复；同机共享磁盘和网络，不能据此宣称跨机器高可用。

## 持久维护闸门与目标合同（M4-03A）

011 是显式增量迁移，只新增维护闸门、目标版本、消费进度绑定和控制日志。创建及所有动作／评论事务先对闸门单例行执行 FOR SHARE，直到原业务事务提交或回滚才释放；原有用户、工单、团队和成员锁随后获取。冻结操作对同一行执行 FOR UPDATE，只有全部已准入业务事务结束后才能持久化冻结并确认，因此冻结标记不是独立于提交的 Middleware 检查。

冻结没有自动到期或进程租约。崩溃不会解除冻结，恢复必须提供本次 freeze_id，在排他锁内改回 OPEN，再读回状态和修订号确认。CDC 检查点、水位、消费处置和 M4 控制数据使用各自已有事务。登录会话属于身份数据，保留可用。批量夹具导入不属于正常业务入口，拒绝安装了 011 的源库。任意直连 SQL、旧二进制与迁移安装期间尚未参与闸门的事务必须由部署流程隔离，不能由这条记录锁自动约束。

目标版本包含 MySQL 源、Kafka 身份与分区、ES／CK 端点及 UUID、当前／后续写入者和进度归属。首次登记现有目标才可创建 ACTIVE；候选登记只能创建 PREPARED。准备候选时复用 M4 任务锁、快照哈希和身份检查，并在持久冻结下重新执行当前全量对账。记录报告哈希和冻结修订号，保持 handoff_verified=false，没有 PREPARED 到 ACTIVE 的推广入口。旧 consistent 报告和进程启动均不能代替本次核验。

受管理 API／标准消费者必须显式配置目标版本，启动和运行检查都核对实际客户端目标及进度来源；失败不创建或改用其他目标。新游标同时携带版本 ID 和不可变合同摘要。受管理 CDC 另查询实际 Binlog TCP 端点的服务器 UUID，避免把状态库身份当作捕获源身份。身份查询属于检查；候选写入归属和消费位置交接由下面的 M4-03B 合同承担。

完整验证和安装步骤见 [M4-03A 交付](m4-03a-delivery.md)。

## 候选消费位置交接（M4-03B）

012 显式新增交接、逐分区确认、物理目标写入者、操作日志和按版本隔离的投递／心跳／水位表，保留旧 ACTIVE 表及共享 CDC 检查点。交接引用 PREPARED 的不可变身份合同，动态 owner epoch、心跳和阶段不改变搜索游标指纹。阶段为 DRAINING → PINNED → OFFSETS_READY → CONSUMING → VERIFIED，没有推广到 ACTIVE 的入口。

DRAINING 持久请求 M4 follower 排空，阻止普通 Run／Check／Follow 再进入。封存控制器连续持有任务锁、两端目标锁和业务冻结保护，有限追平、全量对账并核对所有分区的同一源标记；将实际持久 next_offset、报告和两个 sealed owner 原子提交为 PINNED。冻结确认后不允许未完成的交接恢复业务写入。

两个新组以 Topic、组件、目标版本确定。启动前用 kadm.CommitOffsets 精确提交 pinned next_offset，逐分区检查返回错误并用原始 FetchOffsets 读回。提交前先保存意图，部分成功、超时或进程退出只允许在未开放消费时补齐同一向量。CONSUMING 在启动工作进程前持久提交，此后永远禁用初始化；恢复只能使用当前 Kafka committed offset，并检查 Topic 身份、完整分区集合和保留范围。候选使用 AtCommitted，旧默认组行为保持。

每个候选组件只允许一个合作写入进程。共享 MySQL 元数据库中的物理目标 named lock 与持久 owner／epoch 同时参与准入；写入和进度保存前再核对归属。空闲锁不能单独证明旧进程停止，只允许已清理的 owner 或已确认死亡的同机 PID 接续。失去锁连接、身份不匹配或 Kafka session 丢失时拒绝后续写入。这个方案不提供 ES／CK 请求级 fencing：连接失效前已被后端接受的请求可能迟到完成，远端未知 writer 也不会自动接管。

验证另发新源标记，要求两个新组的所有分区完成投影并提交越过标记，候选无未完成／隔离失败，两端内容再次全量一致，当前 owner、心跳及单成员 Stable 组均匹配，才保存 VERIFIED。Search freshness 与 Analytics status 的候选读器只读对应版本的新组状态；API 仍用原 ACTIVE 的状态读器。协议、故障恢复和范围见 [M4-03B 交付](m4-03b-delivery.md)。

副本数和最小 ISR 是显式部署配置，既有 Topic 不匹配时拒绝启动，副本迁移需另行审阅。新 Topic 创建确认后有界等待元数据传播，再核对实际配置。幂等生产者的进行中请求在结果未知时可能超过客户端记录交付期限；发布调用用回调与 12 秒截止时间分别处理。到期返回未确认，迟到 ACK 不改变本次返回或推进 CDC 检查点，下一轮从原检查点安全重放。该处理保留幂等序列，不把超时解释为消息肯定未写入。

## ClickHouse 指标模型（M3-01）

[ClickHouse DDL](../db/clickhouse.sql) 是两张表的结构来源。[统计 SQL](../internal/analytics/clickhouse.go) 按业务版本归并，普通 MergeTree 不承担去重承诺。历史以组织／工单／版本唯一，当前快照按最大版本选择；同版本旧 schema 的不完整行优先级较低。重复会增加物理行，每次查询先归并，暂停合并时结果也正确。

历史初始化在 MySQL 一致快照中读不可变前后状态，再补当前行。初始团队、事件团队、首次解决时间来自历史版本；JOIN 当前工单仅取不可变身份和创建时间。旧历史经同一 Kafka Topic 入库，重叠增量按事件键和版本去重。先写事实再写状态，两者成功才提交 Offset；部分成功重读两表，最终恢复一致。授权、时间与下钻口径见 [API](api.md) 和 [M3-01 交付](m3-01-delivery.md)。
