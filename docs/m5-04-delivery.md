# M5-04 搜索稳定性与权限查询放大

本轮回答搜索失败发生在哪一层、低授权选择性会放大多少查询，以及两项局部调整是否保留权限和分页正确性。所有实验均在独立 MySQL、Elasticsearch 和 HTTP 应用完成，未修改 CK 统计模型、M4 恢复协议或原演示数据。

本轮复现的搜索不可用由客户端临时端口耗尽引起。相同原始团队过滤负载重复两次，默认 HTTP 连接池分别产生 5,114、4,543 次错误，全部在收到 ES HTTP 状态之前返回地址不可用。增加有界空闲连接复用后，同负载两次均无错误。M5-01 未保存底层错误链，历史全部错误的根因仍为 **UNKNOWN**；本轮复现不能替代缺失的历史证据。

低授权比例还存在独立的查询放大。每页 20 条在 1% 授权下通常需要扫描接近 2,000 个候选，固定 100 条批次带来约 20 次 ES 查询和 MySQL 复核。将后续批次按有效命中率调整到最多 400 条后，10 万数据的 60 秒稳态复核次数降到 6 次，成功吞吐提升约 40%～53%，尾延迟下降。候选数量、最终 MySQL 权限复核和预算错误仍保留，无法在 1% 场景承诺完整的普通分页。

## 1. 真实调用链和冻结合同

以下链路重新读取 live repository，并保存了修改前源码：[原搜索链路源码](../artifacts/m5-04/chain/)、[源码基线清单](../artifacts/m5-04/baseline-source-manifest.json)。

| 环节 | live 位置 | 实际行为 |
| --- | --- | --- |
| HTTP | internal/httpapi/search.go，internal/httpapi/api.go | 当前服务器凭据查用户；解析参数；请求上下文 10 秒；新增服务器随机请求 ID |
| 搜索服务 | internal/search/service.go | 先读投影新鲜度，再开启请求内只读 RR 授权事务；不得重新引入 M5-01 的嵌套连接等待 |
| ES 候选 | internal/search/elasticsearch.go | 必须限制组织；普通用户按创建者或当前 MySQL 成员团队粗筛；只读 ID/version；不请求原始总数 |
| MySQL 复核 | internal/mysqlstore/search.go | 候选 ID 批量 IN 查询，当前组织、创建者或当前有效团队成员授权；返回字段全部来自 MySQL |
| 版本判定 | internal/search/service.go | 候选版本必须与当前只读快照中的工单版本严格相等，否则跳过 |
| 页结果 | internal/search/service.go | 收集 page_size+1 个有效结果才证明有下一页；游标取最后返回项的排序值，下一批 ES 查询取最后扫描候选的排序值 |

原实现每批 100，单请求最多扫描 2,000。页大小仍为 1～100，关键词最多 200 个 Unicode 字符，排序仍支持更新时间、创建时间、优先级、ID，非 ID 排序以 ID 作同方向第二排序键。时间筛选为 UTC RFC3339、左闭右开。游标仍为 AES-GCM，加密绑定用户、组织、除游标外的全部查询参数，1 小时有效；没有引入 PIT 或跨页数据库快照。

授权事务在 ES 往返期间保持一条 MySQL 连接，确保请求内身份、成员关系和返回字段采用一致读。每个请求重新建立快照，因此成员撤销、转派在后续请求生效。并发写入时遵守原“最终一致投影 + 当前 MySQL 授权”合同，不承诺跨请求的静态全集；滞后版本可造成暂时遗漏，不能泄露旧归属工单。

返回总数仍为 null，关系为 unavailable，不能展示未经授权的 ES 原始命中数。候选短批可返回终页、空页或授权不足短页；满批耗尽预算且未能证明完成/下一页时仍返回 HTTP 422 / SEARCH_TOO_BROAD，不返回部分结果。批次变大时如果在最后剩余预算处恰好满批，仍需要证明结束，不能越过预算补查。

MySQL 批量授权 SQL 未改。其核心条件如下；完整字段、JOIN、100/400 ID 展开与实际计划见 [执行计划](../artifacts/m5-04/plans/)。

~~~sql
WHERE t.organization_id=? AND t.id IN (...)
  AND (t.creator_id=? OR EXISTS (
    SELECT 1 FROM team_members m
    JOIN teams tm ON tm.organization_id=m.organization_id AND tm.id=m.team_id
    WHERE m.organization_id=t.organization_id
      AND m.team_id=t.current_team_id AND m.user_id=?
      AND m.active=TRUE AND tm.active=TRUE
  ))
~~~

主管省略上面的个人/团队条件，仍受组织条件限制。实际计划为工单主键范围访问、成员主键单行查询与团队/负责人主键 JOIN，没有全表授权扫描。10 万夹具的单线程 EXPLAIN ANALYZE 中，100 个 ID 约 0.204 毫秒、400 个 ID 约 0.779 毫秒；扩大批次减少的是网络和事务往返，单批 SQL 并不会更便宜。

ES 请求保持 allow_partial_search_results=false、3 秒查询超时、HTTP 客户端 5 秒总超时。候选查询没有新增应用重试；Go transport 原生可重试条件仍由上游实现处理。非 200、传输失败、坏 JSON、响应缺字段、分片失败或无效候选仍映射 SEARCH_UNAVAILABLE；上下文/ES 查询超时映射 SEARCH_TIMEOUT；MySQL 超时按既有 API 规则映射 REQUEST_TIMEOUT，其他数据库错误按原合同映射 INTERNAL_ERROR。

## 2. 隔离环境、数据和采样方法

主机为 macOS arm64、48 GiB、18 个逻辑 CPU，开始时可用磁盘约 248 GiB。MySQL 8.4.5 独立端口 33309，缓冲池 64 MiB、最大 64 连接；ES 8.17.5 独立端口 19202/19302，堆 512 MiB，原 mapping 的单分片、零副本、1 秒 refresh。应用 18087 使用正式 HTTP handler 和 mysqlstore.Open 的 20 open/10 idle 池；未增加 MySQL 池或 ES 堆。Native 进程没有 cgroup/RSS 硬配额，不能把堆配置当整机独占资源。有效设置和二进制校验在 [环境证据](../artifacts/m5-04/environment/)、[最终有效设置](../artifacts/m5-04/environment/final-runtime/)。

冻结生成器保持 ticketpulse-benchseed/v1、seed=20261109：1 万工单/97,500 历史/26,500 评论，10 万工单/975,000 历史/265,000 评论。两份业务 Bundle SHA256 分别与 M5-01 一致，原始数据库和 ES 索引单独保存。所有原始业务键和版本经独立 SQL/ES 全量对照一致：[数据 manifest](../artifacts/m5-04/datasets/)、[全量核对](../artifacts/m5-04/correctness/frozen-full-audit/)。

授权选择性采用另一份只读当前状态故障夹具。按固定随机种子把 ID 打乱分到 100 个等大桶，MySQL 团队按桶重映射，四个专用 agent 分别属于 100、50、10、1 个桶；没有创建者权限旁路。ES 当前团队统一保留为专用旧团队，四个用户均属于该旧团队，因此同一候选全集下当前授权比例精确为 100%、50%、10%、1%。字段、版本、时间、状态、关键词和工单数量保持冻结规则。独立 SQL 核对分别为 10,000/5,000/1,000/100 和 100,000/50,000/10,000/1,000 个有权工单。

该夹具是人为的同版本归属错误，用于隔离授权选择性；不能把它描述成合法 CDC 可产生的同版本变更。真实转派会提升版本，另通过业务 API、Kafka 和暂停/恢复消费验证。夹具推导与限制见 [选择性定义](../artifacts/m5-04/datasets/100000/selectivity/derivation.json)。

正式短测为每组预热 2 秒、采样 6 秒，两个规模 × 四比例 × 10/50/200 并发；A/C/D 增加第二轮倒序 A/B，B 保留第一轮。10 万较长稳态为预热 5 秒、采样 60 秒，50/200 并发；另有明确命名的 1% page10 实验。原始失败重跑使用原 2 秒/8 秒、客户端 5 秒超时和原随机路由脚本；容量矩阵客户端 12 秒、服务端 10 秒，不能把不同超时窗口直接当历史容量提升。

所有负载都是固定并发闭环、HTTP keep-alive。成功 QPS 的分母包括最后请求排空，失败不计成功；p50/p95/p99 是全部请求延迟，成功延迟另保存在原始结果。预热、正式采样、后台写入均独立记录。没有添加拒绝/排队入口，MySQL 原连接池的排队时间单独观测；预算 422 是原业务合同，不能算吞吐成功或限流收益。

安全预算为测试运行目录 8 GiB、独立进程合计 RSS 8 GiB、ES 已用堆 90%、剩余磁盘至少 20 GiB，达到即停止。正式矩阵无预算停止、无非预算搜索错误；全部采样 ES 堆最高 76%，搜索线程池拒绝增量为 0。最初资源采样因错误 ES metric 名失败、随后一次监控连接遭临时端口耗尽，均保留失败输入，未作为容量样本。

## 3. 搜索不可用复现与诊断

新诊断将随机请求 ID 返回在 X-Request-ID，并传至 ES X-Opaque-ID。服务器内部记录身份读取、投影新鲜度、事务开始、连接占用、累计 ES/MySQL 耗时、ES 状态/有限错误类别、候选批次/数量、MySQL 有权数、版本拒绝数和实际返回数。MySQL 查询计数是数据 SELECT 的调用次数，不包含驱动发出的事务控制语句；事务开始、关闭和排队成本另计入连接耗时。连接获取与 BEGIN 的耗时合计记录，无法仅凭该字段精确拆分；全局 DBStats 的 WaitCount/WaitDuration提供独立排队证据。失败日志不包含原始错误正文、Cookie、Bearer、关键词、游标或工单正文；全量成功诊断仅由隔离 benchmark observer 写入本轮证据。

这不能证明 M5-01 混合场景一定由端口耗尽导致。M5-01 原始失败响应没有 ES 状态、transport errno或关联日志；M5-02 曾使用不同观察链路且未复现。历史根因继续 UNKNOWN，本轮已复现子集与未复现子集分别标注，不进行猜测性统一归因。

受控注入另外验证了五种 SEARCH_UNAVAILABLE、两种 SEARCH_TIMEOUT 和一次正常恢复。ES 拒绝/熔断、坏 JSON、分片失败、查询超时、HTTP 客户端超时、断连均可分类，公开错误合同保持一致，敏感 marker 不出现在服务器日志。这是诊断能力验证，不能用于证明历史原因：[失败/恢复结果](../artifacts/m5-04/failures/classified-faults/results.json)。

## 4. 两项优化及取舍

只采用两项局部性能调整。第一项将 ES 客户端 transport 克隆为私有实例，空闲池设为总计 64、每主机 32，保留原 5 秒客户端超时和 native transport行为。没有设置 MaxConnsPerHost，也没有拒绝、缩小页或新增服务排队。它消除了可重复的端口耗尽，同时避免把全局 DefaultTransport 改成项目配置。

第二项保留首批 100；已扫描候选中有效授权且版本相等的比例不足 25% 时，按尚需结果和当前命中率估算后续批次，以 100 向上取整，最多 400，最后批次裁到剩余预算。它不缓存权限、不信任 ES 归属、不改变 MySQL SQL，也不突破 2,000 候选。对静态候选序列，分组变化不改变有效项顺序；has_more 仍由第 page_size+1 个有效项证明，游标仍指向最后返回项，下一请求重读当前权限。

本轮未新增索引、预授权缓存、PIT、分页协议、限流或大规模重构。MySQL 当前查询已使用主键范围，EXPLAIN 未给出值得额外加索引的证据；低选择性来源是滞后/错误候选，不适合把 ES 权限直接当最终权限。提前释放授权事务会改变请求内一致读，未采用。更大批次会增加单次响应和 SQL 内存，因此上限为 400；不会消除约 1/选择性的候选成本。

10% 稳态只提升约 1%～5%，50 并发 p99 从 73.1 变为 74.5 毫秒，不能宣传所有低比例查询都明显更快。100% 稳态约下降 4%～9.5%，而两轮短测基本持平；该路径仍是首批 100、一次复核，不能把这组波动算作正向收益。10 万 C/200 第一次短测出现 p99 3.61 秒，后续重复为 339 毫秒、60 秒为 355 毫秒；保留离群样本，不能只引用第一次对照宣称两倍提升。

服务器资源与连接占用共同定位了放大成本。1% 基线 50 并发的连接获取/BEGIN p99 约 206 毫秒，200 并发约 1,293 毫秒；ES 时间合计约 47～48 毫秒、MySQL 授权合计约 40～41 毫秒。已用堆、GC 和线程池拒绝未显示 ES 资源崩溃，因此此资源配置下首先受多批 ES/SQL 往返和 20 连接池排队约束。原始资源 JSONL和 SQL digests 保存在每组结果目录及 [计划证据](../artifacts/m5-04/plans/sql-digests-after-steady.tsv)。

## 8. 结论与未验证边界

真正的瓶颈分为两层。本轮可重复的搜索不可用是默认 ES HTTP连接复用不足导致临时端口耗尽；解决后，低授权选择性的多批候选查询和授权事务持有连接成为主要成本。MySQL单批主键授权已有良好裁剪，测试中 ES没有内存/线程池拒绝，增加ES堆不是本轮有效代码优化证据。

查询放大确实存在。高授权页20仍固定扫描100条，约5候选/返回项；10%约13.7，1%约100，而且失败请求还消费完整2,000候选但返回0条。后续批次优化减少复核次数、SQL/网络往返和连接占用，没有消除选择性固有成本。

当前可验证的并发上限只能按分布解释。ES512MiB/MySQL64MiB/池20的10万数据，200并发已在60秒采样内通过高授权和10%普通查询；高授权p99约205毫秒，10%约344毫秒。若希望低选择性尾延迟较低，**50并发是本轮更合理的运行点**：1%普通页20最终p99约344毫秒，而200并发约1.58秒且完成吞吐仅增加约8%。1%普通页20无论10、50、200并发都存在预算错误，不能宣称支持完整成功分页。没有业务SLO与开放到达率测试，不能把本地闭环数据直接当生产容量保证。

优化未牺牲最终MySQL授权、版本匹配或游标合同，18组完整结果前后一致。连接复用改善故障与尾延迟证据明确；后续批次调整在1%场景收益明确、10%较长稳态收益有限、高授权没有普遍收益且有负向样本。200并发的尾延迟仍明显劣于50，吞吐数字不能掩盖排队。

历史SEARCH_UNAVAILABLE没有统一归因：已复现的团队过滤子集有本轮端口耗尽证据，未复现的历史混合场景仍UNKNOWN。新增内部诊断使以后可以按层定位，不再仅保留一个公开503。

未验证超过200并发、超过10万工单、跨主机网络/TLS、真实开放到达率、多副本多分片ES、长时大量成员、批量转派、持续几小时以上混合写入及跨页更新引起的重复/暂时遗漏边界。本轮较长稳态为60秒/组，不能代替耐久或峰值容量实验。没有新增授权索引或重大协议调整；若以后需要在1%甚至更低选择性下保证普通完整分页，需要先审阅候选/授权/分页设计，不能直接信任滞后的ES权限。
