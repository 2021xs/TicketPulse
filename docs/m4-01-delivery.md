# TicketPulse M4-01：数据重建、自动对账与故障恢复

本轮补齐了从 MySQL 重建隔离 ES/CK 投影、断点续跑和自动对账的运行入口。重建完成后保存一份经过同步边界确认的检查报告，原演示索引、统计空间和业务数据继续保留。实际验收使用本项目的 MySQL 8.4.5、Kafka 4.4.0、ES 8.17.5、CK 26.10.2.103，以及真实 HTTP 和 Chrome。

代码基线来自 live repository；本仓仍为无提交的 `feat/m1-01-ticket-loop`。本轮开始前保存了 136 个源文件的哈希和恢复归档，差异以该归档为基准。没有暂存、提交、推送。M1/M2/M3 的已有业务实现及交付证据保留。

## 交付结论

| 判断 | 可核验依据 |
| --- | --- |
| 当前状态和历史可以分别从 MySQL 恢复 | 当前行来自 tickets，历史直接读取持久化 ticket_histories，恢复前校验版本连续性和前后状态 |
| 重建与实时消费者能够并行 | 重建保存独立分区位置，使用相同消息与投影函数，已有两个消费组继续运行 |
| 重复和旧版本不能回退当前投影或增加业务计数 | ES 严格外部版本；CK 查询先归并组织/工单/版本，再取首次事件和最新状态 |
| 完成状态包含追平和对账 | 同一源标记必须被每个分区处理，再检查字段、历史、同键冲突及指标 |
| 中断后可从已确认批次恢复 | 已冻结输入与游标保存在 MySQL；实际 SIGKILL 和投影成功后进度写失败均已验收 |
| 投影或接续窗口再次丢失时明确失败 | 目标 UUID、Topic ID、分区位置和冻结摘要均校验，不静默跳到日志尾 |

核心证据在 [故障验收入口](../artifacts/m4-01/fault-tests/latest.json)、[独立 CLI 验证](../artifacts/m4-01/baseline-runtime/independent-pilot/result.json) 和 [最终演示对账](../artifacts/m4-01/final-regression/demo-check-results.json)。机器输出与独立 SQL/HTTP 观察一起用于验收，程序自行声明完成不能代替数据比较。

## 权威来源与历史完整性

当前投影以 MySQL 工单表的权威行为来源。ES 比较工单 ID、外部版本和全部投影字段，包括标题、描述、状态、当前团队、负责人、类别、优先级、身份和时间。CK 当前状态还比较首次解决时间，空负责人和空时间保留在整行 tuple 中。

历史以 MySQL 业务历史表为来源，实际表名是 `ticket_histories`。每个成功业务动作都与工单版本更新在同一事务中提交，历史保留完整前后状态、事件时间和当时团队；每个工单版本最多一条业务历史。重建只连接当前工单读取组织、编号和创建时间等身份，不用当前团队或当前状态推测过去事件。

恢复统计前，程序检查创建版本、逐版本连续性、前一版本与后一事件的 before 状态、最终历史与当前行。独立对账另外检查首次解决和重开计数，以及缺失/多余历史。源历史缺失或矛盾时返回“无法完成检查”，停止宣称历史已经恢复；没有生成占位历史或反推事件。

PRD v0.2 的完整原文件未出现在现有仓库中。本轮沿用 M3 已冻结的口径及独立十工单 SQL/Gold，没有重新定义统计规则：新增按创建时初始团队；首次解决先取最早 resolved 版本，再按当次团队和日期过滤；再次解决不重算首次；当前积压按当前团队，只包含待处理和处理中。北京时间窗口左闭右开，平均时长以总时长除以首次解决数计算。

## 安全重建与中断恢复

每个任务自动生成新的 ES 索引和 CK 数据空间。任务 ID、目标类型、批次大小和指标参数创建后固定；相同参数重复创建返回同一任务，参数变化明确拒绝。目标名称已存在但没有持久认领记录时拒绝接管，因此不会误写原演示空间。

任务先在 MySQL 一致读事务中按有界批次扫描历史和当前行，将可重放消息、连续序号、数据摘要、源 UUID、源位置及各分区起点一次提交为冻结输入。内存只保留一个批次；整个冻结仍是单个事务，期间中断会回滚并在下次重新冻结。已有冻结输入则先复核数量和摘要，随后从持久批次游标继续。

回填直接调用既有 ES 写入和 CK 历史投影函数，不向业务 Topic 再发布全量快照。每个批次只在全部下游写入完成后保存游标。投影写入成功、游标保存失败时，同一批次允许重放；有限重试耗尽后保存失败阶段和原因，后续由同一任务继续。CK 两表部分成功也按既有业务键语义恢复。

任务状态、逐分区下一位置、源标记、错误、完整对账报告和过程日志均可查询。状态另外显示工作进程是否实际持有任务锁；SIGKILL 后可能留下最后一次 running 状态，但持锁标志为 false，不会误表示进程仍在工作。同一任务只允许一个执行者；不同任务可以写各自的隔离目标。

## 全量和实时增量如何衔接

Kafka 分区起点在 MySQL 快照建立之前读取并冻结。捕获器已经读取但尚未发布的事务，以及冻结期间新提交的事务，都落在重建的重叠区间。重建按自己保存的位置读取原 Topic，不改变 CDC 检查点，也不提交现有 ES/CK 消费组的 Offset。

ES 文档 ID 等于工单 ID，严格外部版本只接受更高业务版本；先到的新版本不会被迟到的旧快照覆盖。CK 当前候选按最大 `(version, complete)` 取整行，历史事实按组织/工单/版本归并，传输重放不会增加规范业务事实数。后台 merge 不承担正确性；物理行可能增加，业务计数保持不变。

回填结束后，任务在 MySQL 提交新的源标记，由原捕获器通过同一 Binlog 和 Topic 发送到每个分区。所有分区处理该标记后才开始完成检查。对账先冻结源读视图，再确认读视图之后的另一源标记，解决标记附近新写入的竞争；检查结束后再次读取源摘要，run 遇到期间变化会在有限时间内重新接续并重查。check 只执行一次，遇到源变化保存尚未追平报告并退出非零，需要调用者重试。有限等待超过截止时间明确失败，不将永久错误描述为无限同步延迟。

一个完成报告只证明报告对应时点的数据一致。候选需要继续接收新增量时运行长期跟随模式；停止后使用 run/check 再次获得新的证明。现有应用使用直接配置的索引和 CK 数据空间，本轮没有增加自动别名切换或配置发布。实际切换时需要短暂冻结业务写入、完成最终核对，再按源标记和候选分区位置协调消费者接续；仅改服务配置而沿用旧消费组进度仍需人工审查。

## 自动对账

对账逐页读取 MySQL、ES 和 CK，明确检查缺失和额外的工单/历史。ES 使用 PIT 与 search_after 保持目标分页视图；CK 读取规范当前行和每个历史键，同时计算同键内容种类，避免 any/argMax 隐藏矛盾事实。指标另由 MySQL 历史独立聚合，比较正式 CK 指标查询。任务指定指标组织不会缩小重建的全库检查范围；直接 check 不带任务 ID 时，指定组织会同时限定字段/历史检查范围，组织为 0 才检查全库。

检查有单批响应和差异保存预算；超过预算明确报无法完成，或者继续统计完整差异总数并标记明细截断，不把部分结果当完整成功。四种状态按下表判定。

| 状态 | 语义 | 后续动作 |
| --- | --- | --- |
| consistent | 同步边界已确认，源未变化，全部检查相等 | 保存报告，候选继续跟随或进入人工切换评估 |
| catching_up | 捕获/消费尚未达到冻结边界，或检查期间源发生变化 | 在有限时间内接续并重查 |
| inconsistent | 边界已确认且源稳定，字段、键、历史归属或指标仍有差异 | 保留差异，修复原因后新建隔离候选 |
| uncheckable | 源历史不完整、组件不可用、响应不完整或截止时间内无法确认边界 | 保留错误，检查依赖和源证据后重试 |

ES 同版本标题被人为改坏、CK 同一业务键写入矛盾团队时，实际对账返回不一致。CDC 停止但 HTTP 写入继续时，首次观察为尚未追平，有限等待后为无法完成。源历史缺失的独立测试也会失败，而不会与同样缺少事实的投影一起被判一致。

## 真实故障与回归验收

所有破坏性注入都只操作随机测试库、Topic、索引和统计空间。测试保存原始 MySQL 行、ES HTTP 响应、CK 物理表、独立规范 SQL、任务时间线和实际命令。旧演示库以及之前各轮证据未删除。

| 场景 | 实际结果 |
| --- | --- |
| 删除已构建的隔离 ES 索引 | 原任务因目标身份丢失拒绝继续；新任务重建相同权威数据 |
| 清空隔离 CK 两表 | 新任务恢复全部历史和当前状态，PRD 数值不变 |
| 回填期间持续 HTTP 写入 | 创建、解决、重开和跨多个批次的评论与实时消费者并行，最终最新版本收敛 |
| 已保存游标后中断 | 原任务从已确认批次恢复，不重新扫描业务源 |
| 下游写入成功、进度提交前失败 | 实际 MySQL 触发器中断保存，恢复产生物理重复但规范事实/指标不增加 |
| 实际 SIGKILL 重建 CLI | 观察到持久批次进度后杀死进程，同一任务恢复并独立核验数据 |
| 同一任务重复 run | 复用冻结输入和分区位置，不重复全量回填，规范结果不变 |
| 旧版本与新版本交错/重复消息 | ES 保留新版本；CK 最早解决事件和团队归属正确 |
| Kafka 旧消息删除到分区末尾 | 新任务仍从 MySQL 恢复完整 46 条历史，不依赖旧 Kafka 事件 |
| 已冻结的 Kafka 重叠窗口被删除 | 旧任务明确报位置过期，新任务重新冻结恢复 |
| 长期跟随取消/恢复、Topic 身份变化 | 取消后续接新增量；同名 Topic 更换明确停止，避免沿用旧位置 |
| 指定组织指标但另一组织投影丢失 | 全库对账仍发现缺失，新任务恢复两个组织 |

PRD 十工单恢复后的独立预期为新增 10、首次解决 6、平均 60600 秒、当前积压 5；团队 10 的积压 ID 为 `[10]`，团队 20 为 `[3,4,6,8]`。转派后的历史首次解决保留事件团队，重开和再次解决没有增加首次解决计数。结果来自固定 Gold 和独立观察，并非通过正式 SQL 生成预期。

最终完整 M4 套件为 10 项，全部通过并开启 race，耗时 62.126 秒。实际 SIGKILL 时已确认 2/56 条输入，杀进程到恢复完成独立核验为 2.056177 秒。投影已写入而游标提交失败的恢复留下 48 个 CK 物理历史行与 58 个物理状态行，分别规范为 46 条历史和 10 张工单，指标不变。以上时长是本机小样本故障观察，未作为性能或恢复服务等级承诺。

M1 真实 MySQL 集成/race 77 项、M2 7 项、M3 2 项均通过；Chrome 的 M1 4 场景、搜索主流程和 PRD 看板场景也通过。本轮为保留演示服务，未再次运行会停止共享 ES/CK 的旧浏览器故障场景；本轮实际下游故障、消费暂停及隔离恢复由真实集成覆盖。最终 race、vet、构建和 M2/M3 回归的命令与结果集中在 [最终回归目录](../artifacts/m4-01/final-regression/)。

演示自动对账覆盖 5 张工单和 29 条历史，两次检查均一致、差异为零。独立哈希比对另外覆盖九张 MySQL 业务/身份表、5 个 ES 文档及外部版本、29 个 CK 物理事件行和 39 个物理状态行，与本轮基线相同；[保留结果](../artifacts/m4-01/final-regression/demo-preservation-final.json) 为 true。同步控制水位在演示进程持续运行时自然前进，没有把其变化误写为业务数据变化。

## 操作入口与人工恢复

已有实例先应用追加迁移，迁移只创建四张控制表。现有本机辅助入口核验项目 UUID，使用私有凭据；日志与报告不保存密码、Cookie 或凭据原文。外部部署需要管理员应用同一迁移，并为运行账号授予控制表 SELECT/INSERT/UPDATE 和源表读取、源标记更新权限。

~~~bash
make build
python3 scripts/local_rebuild.py migrate
python3 scripts/local_rebuild.py create -job=m4_recovery -target=both -batch-size=100
python3 scripts/local_rebuild.py run -job=m4_recovery -wait=60s
python3 scripts/local_rebuild.py status -job=m4_recovery
python3 scripts/local_rebuild.py logs -job=m4_recovery
python3 scripts/local_rebuild.py check -job=m4_recovery -wait=60s
# 保持候选接收新增量；另一个终端查询 status，结束后重新 run/check
python3 scripts/local_rebuild.py follow -job=m4_recovery
# 只检查原演示投影，不创建任务，不需要 009 控制表
python3 scripts/local_rebuild.py check -target=both -wait=30s
make integration-rebuild
~~~

命令退出非零时先读取任务状态、错误和日志。依赖暂时故障修复后复用同一任务；目标丢失、冻结数据损坏或重叠区间过期时保留失败证据，使用新 ID 从 MySQL 创建新的候选。缺失历史需要先恢复权威源证据，本轮不会自动补造。

跨系统创建目标和保存目标身份之间存在一个小窗口。窗口内进程崩溃会留下未认领目标，下一次运行拒绝接管；操作员应核验其确为本任务空目标后清理，或直接创建新的任务 ID。MySQL/Topic 身份改变时还需按原 CDC 迁移合同恢复正确的捕获检查点，本轮不会自动改写原链路进度。

## 剩余边界

冻结前断点不会保留半份输入；冻结期间杀进程后重新冻结的原子性由事务实现保证，但本轮未对冻结事务内部实施 SIGKILL，真实杀进程覆盖的是已持久投影批次。冻结在一个长事务中完成，会占用源数据库和控制数据空间；本轮没有百万级数据压测，也没有引入跨分页的可过期快照。

CK 的物理重复、冻结输入和任务日志当前持续保留，尚未加入清理策略。所有重建过程依赖源 MySQL 和冻结之后可用的 Kafka 实时区间；旧事件已不可用可以从 MySQL 恢复，但冻结之后的新事件再次丢失必须创建新任务。原始历史未持久化、被篡改或源库丢失仍需备份及人工恢复。

CK 当前候选表的同版本内容冲突能使检查失败，但报告按工单最新版本标识该冲突；若矛盾仅发生在旧候选版本，定位实际版本还需查询物理状态表。历史事实冲突按每个业务版本报告，已在真实故障测试中核验。

Kafka/CK 多节点高可用、断电、磁盘满、跨平台辅助脚本、在线重分区和自动生产切换未验证。当前结论限定为本机真实组件上的功能与有限故障恢复，不扩展为生产多副本持久性或大规模性能结论。

现有 M2/M3 和 M4 测试夹具继承同一复制 server ID，复现时应串行运行两套真实集成；并行会竞争 MySQL 复制连接。一轮回归曾出现既有 ES 恢复等待超时，后续同一套 9 项真实 M2/M3 测试通过；失败记录保留，未将其删除或改成成功。
